# FileButler

本地文件与论文管理 Agent。用一句中文指令，在指定的资料库文件夹里查找、阅读、分类、去重、移动、改名和回收文件，所有写操作都可以撤销。Agent 循环是手写的，不依赖框架；另外配了一套用真实模型跑的验收评测，用数字说明每个设计的效果。

- 模型：DeepSeek `deepseek-flash`（OpenAI 兼容接口）。
- 界面：FastAPI 本地网页（多对话、文件预览、确认卡片）和命令行。
- 规模（2026-10-22）：核心代码约 9,100 行 Python，前端约 1,200 行，评测约 4,300 行，离线测试 643 项。
- 默认配置：`protocol: v3`、`prompt: v9_intent`。v2 协议和 `v8_tasks` 提示词冻结保留，作为对照基线。

## 设计核心：模型说意图，本地管执行和核验

一开始，模型要自己写完整的任务契约（完成条件、写入范围、约束规则）。真实运行里，大量请求都花在纠正契约格式上，而且模型可以写出“看起来完成了”的条件。协议 v3 改了分工：

| 由模型决定 | 由本地代码决定 |
| --- | --- |
| 用户要做哪几件事（`start_task` 的 parts） | 每部分的完成条件、写入范围、目标归属 |
| 用户明确说出的限制（limits） | 限制如何落到具体检查规则 |
| 操作哪些对象：选择集或逐项动作 | 展开清单、排定执行顺序、预检、确认、执行、逐项核验 |
| 请求不清楚时给用户哪些选项（`ask_user`） | 选项是否是工具能做到的，用户看到之前先检查 |
| 给用户的回答（`finish_task.reply`） | 状态是 done、partial 还是 needs_review：由本地核验得出，模型不能自己宣称完成 |

同一套 13 组场景，第 05 轮用 v2，第 08 轮用 v3（每组跑 1 次）：

| 指标 | v2 | v3 |
| --- | ---: | ---: |
| 整组验收通过 | 11/13 | **13/13** |
| 模型请求 | 116 | 81 |
| 被拒绝的调用 | 19 | 0 |
| 纯协议纠错请求占比 | 22.4% | 0% |
| 估算费用 | ¥0.52 | ¥0.23 |
| 模型可见的提示和 schema（字符） | 39,274 | 26,111（−34%） |

## 快速开始（macOS）

```bash
python3.11 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
export DEEPSEEK_API_KEY=...          # 建议写进 ~/.zshrc

uvicorn webapp:app --host 127.0.0.1 --port 8000   # 打开 http://127.0.0.1:8000
python main.py run "把 Inbox 里的 PDF 移到 Archive"
python main.py undo                  # 撤销最近一次运行（也可以指定 run_id）
python main.py search "semi supervised fake news detection"   # 本地 BM25 检索，不调用 API
python main.py dedup --path 文献     # 本地查重，默认只报告
python -m pytest -q                  # 离线测试，使用假模型，不花钱
```

资料库默认是仓库下的 `./sandbox`（见 `config.yaml`）。`gen` 和 `init-demo` 会清空资料库，里面有你自己的文件时会拒绝执行。

## 一次写请求怎么走

1. **登记**：模型调用 `start_task`，按部分列出要做的事和用户说过的限制。`agent/intent.py` 据此在本地生成完成条件和范围。
2. **计划**：模型调用 `prepare_file_plan`，提交选择集（如“文献 下全部 PDF”）或逐项动作。`agent/file_plans.py` 在本地完成以下工作：
   - 展开文件清单，为每个来源记录快照（inode、大小、时间、SHA256）；
   - 按依赖排定顺序：先腾出被占的名字再放入，先移出文件夹里的文件再移动或回收这个文件夹；互换名字这类循环直接拒绝；
   - 检查重名、权限和用户限制，自动补上需要创建的父目录。
3. **确认**：网页上显示一张确认卡片，列出全部来源和目标，超出原登记范围的对象和用户的文字限制也会列出。
4. **执行**：确认后重新检查一遍，逐项用禁止覆盖的原子改名（macOS `renamex_np`、Linux `renameat2`）执行，每一项立即写入操作日志。中途中断时，只按日志续做，不猜测结果、不重放。
5. **核验与回复**：用同一份清单核对每个文件的位置和内容，再由本地生成状态和事实摘要，模型的 `reply` 附在后面。

只读请求（查找、统计、解释）不需要登记，直接回答，结论引用本地给出的文件和证据标识。

## 安全设计

- **没有删除**：只有移入资料库内的回收区，整次运行可以撤销；撤销按日志逆序执行，遇到冲突就跳过，不覆盖。
- **路径不出资料库**：`resolve()` 之后必须仍在资料库内，拦截 `..`、符号链接和绝对路径。macOS 的大小写折叠、连字 `ﬀ`、NFC/NFD 差异都会换成磁盘上的真实名字处理。
- **回收文件夹按风险分级**：
  - 系统元数据（`.DS_Store` 等，名单经过内容核验）：在确认卡片上逐个列出；
  - 其他隐藏文件（如 `.env`）：先问用户，并用本地密钥扫描加强警告；
  - 锁文件（`~$*`）：拒绝，提示先关闭对应程序；
  - 隐藏文件夹、符号链接、应用包：一律拒绝。
- **文件名隔离**：名字里的换行、控制字符、双向控制符和尖括号，在交给模型之前统一转义，确认卡片上标成 `⟦U+202E⟧` 这样的可见形式，并写明实际扩展名。每次工具调用多遍历一次资料库，316 项耗时 2.9ms。
- **文件内容是数据**：正文包在 `<file_content>` 标签里，文件名也按数据处理。真实评测里的注入场景，模型都没有照做。

## 评测

生产 Agent 验收入口是 `eval/live_policy.py`。判定（`eval/judge.py`）分四个维度：文件结果、任务状态、主答复、约束，四个都通过才算通过；效率只作观察。用新判定离线重判 10-21 第 01 轮，结果从旧口径的 8/8 变成 4/8，和人工复核一致。

```bash
python -m eval.live_policy --dry-run --suite blind --out <新目录>      # 脚本模型干跑，不花钱
zsh -ic 'python -m eval.live_policy --live --suite blind --protocol v3 --out eval/results/<新目录> --total-cap 0.3'   # 收费
python -m eval.rejudge eval/results/<已有目录> --out <新目录>          # 用当前判定离线重判
python -m eval.protocol_errors eval/results/<目录>...                 # 协议错误归因
```

套件：`regression`（8 组）、`holdout`（5 组）、`blind`、`blind2`（各 8 组，运行前提交冻结）、`hidden`（隐藏文件，7 组）、`p0`、`p1`（10-22 新功能验收）。输出目录必须是新的，不会覆盖已有结果。

**两套盲测各重复 3 次，v3 与 v2 对照**（第 20 轮，16 组 × 3 次 × 2 种协议）：

| 协议 | 通过 | 95% 置信区间 | 被拒调用 | 费用 |
| --- | ---: | --- | ---: | ---: |
| v3 | 47/48 = 97.9% | 89.1%–99.6% | 2 | ¥0.575 |
| v2 | 35/48 = 72.9% | 59.0%–83.4% | 25 | ¥0.978 |

v2 的失败大多是主答复没有回答用户顺带问的问题，这是 v3 用 `finish_task.reply` 解决的；所以差距里有一部分来自 v3 新增的能力。

**反问实验 E4**（第 24 轮，8 对"缺信息 / 补齐信息"配对场景，各 3 次）：有歧义时提问 23/24 = 96%，从不猜着写入（0/24）；信息清楚时多问 4/24 = 17%，4 次问的都是"目标文件夹不存在时建在哪里"。目标已存在的配对，多问 0/12。

**规则误伤测试**（第 28、29 轮，8 组表面上会碰到本地规则的正常请求，各 3 次）：多问或被拦 0 次。顺带发现一个 bug：文件移到不存在的无扩展名路径时被当成改名，已修复。

其余功能验收（**每组只跑 1 次**，费用是按配置费率的估算）：

| 轮次 | 内容 | 结果 | 费用 |
| --- | --- | --- | ---: |
| 08 | v3，回归 + holdout 13 组 | 13/13 | ¥0.23 |
| 09 | 第一套盲测，首次运行 | 7/8（主答复缺回答，随后修复） | ¥0.09 |
| 10、11 | 第二套盲测；第一套重跑 | 8/8、8/8 | ¥0.19 |
| 12–14 | 隐藏文件分级、选项检查、文字同意 | 5/5、6/6、7/7 | ¥0.27 |
| 15、16 | 文件名注入、翻页平铺、锁文件、提问后发新请求 | 4/4（第 15 轮一组判失败是检查写错，修正后重跑通过） | ¥0.10 |
| 17、18 | 依赖排序：平铺重名、只改大小写、清空后改名文件夹、互换名字 | 4/4（第 18 轮修复跨计划核验后通过） | ¥0.07 |

完整过程见 [docs/live-acceptance-2026-10-21-rounds.md](docs/live-acceptance-2026-10-21-rounds.md)。证据边界：
- holdout 和第一套盲测已经参与过调试，不再算盲测；
- 第 12 轮之后的套件是功能验收，场景和产品出自同一人；
- 只有两套盲测重复了 3 次；其余功能验收每组只跑 1 次。

## 设计决策与依据

| 决策 | 依据 |
| --- | --- |
| 预算按费用算，不按 Token 算 | 七八成 Token 命中前缀缓存，单价只有 1/50。按 5 万 Token 设预算时，300 个文件的 B10 任务 0/5；改为每次 ¥0.30 后 5/5 |
| 上下文压缩默认关闭（E6） | R06 上 Token 减半，费用反而 +25%：压缩改写了旧消息，缓存命中率从 87% 降到 45% |
| 契约由本地生成（协议 v3） | 第 05 → 08 轮：协议纠错请求 22.4% → 0%，费用 ¥0.52 → ¥0.23（见上文） |
| 批量操作走计划和选择集，不逐个调用工具 | 130 个文件平铺用一个计划完成，模型一页列表都没翻，第 16 轮共 6 次请求；先登记任务时，500 项计划准备 0.37s、执行 4.85s |
| 状态由本地核验得出，模型说了不算 | 旧口径 8/8 的一轮，四维判定为 4/8，和人工复核一致 |
| 失败先做成离线回放，再修 | 1/70 的随机漏文件靠重跑复现不出来；录下模型输出做成确定性测试，修复前先确认测试会失败 |
| 结束前自检默认关闭 | 在已漏移文件的位置回放：关闭时 10/10 失败，开启时 10/10 补救成功，每次运行多花约 12%。保留作对照实验 |

## 早期实验（2026-10-07 前，旧控制器）

在 51 篇真实论文上，每个任务跑 5 次：R01–R05 都是 5/5，R06（51 篇打散后重新分类）4/5。合成的 37 个任务通过率 95%。R04/R06 起初只有 1/5、0/5，逐条分析后，原因在 PDF 解析库、任务描述和文件系统特性，模型真正判断错的只有 1 次。

真实数据暴露的工具问题：
- 文件名首尾有空格；
- 长目录列表被截断；
- pypdf 抽出乱码，已改用 PyMuPDF；
- 连字 `ﬀ` 被 macOS 折叠，导致撤销还原不回原名。

这些都已修复，详见 [docs/experiments.md](docs/experiments.md)。旧控制器和这些实验命令（`python main.py eval ...`）仍然保留，复现时设置 `task_runtime: false` 和对应的旧提示词。

## 代码结构

```

webapp.py             FastAPI：多对话、文件预览、确认与撤销接口
web_confirm.py        确认卡片：分组、预览、范围新增、名字特殊字符标记
web/                  前端（app.js、tasks.js、样式）
agent/
  loop.py             主循环：调模型 → 校验并执行工具 → 回填结果；名字隔离在这里统一处理
  task_runtime.py     任务控制器：v2/v3 协议、工具可见性、权限与约束检查、ask_user
  intent.py           v3：从模型给的部分和限制，编译出完成条件和范围
  file_plans.py       文件计划：清单、快照、依赖排序、确认、原子执行、中断恢复、核验
  completion.py       文件集合类完成条件的执行前快照
  constraints.py      本地操作谓词（范围、扩展名、数量、内容不变……）
  verifier.py         逐部分核验；证据有效不等于语义正确
  reporting.py        主回复：本地事实、未完成原因、模型回复
  system_files.py     系统文件名单（system_files.json）与内容核验
  secrets_scan.py     隐藏文件的密钥扫描，只加强警告
  task.py             任务模型、修订与 SQLite 持久化
  artifacts.py        文件 F、证据 E、计划、回执标识
  repetition.py       重复调用与无进展保护
  llm.py / prompts.py 模型调用与计价；提示词版本
tools/                list_dir、search_files、read_file、inventory、BM25 检索、去重、分类、旧单项写工具
safety/               sandbox.py 路径；atomic.py 禁止覆盖改名；oplog.py 日志与撤销；
                      confirm.py 终端确认；names.py 文件名转义
eval/                 live_policy.py 验收入口；judge.py 判定；*_cases.py 场景；旧实验 runner/generator/replay
tests/                离线测试（假模型），含真实 trace 的回放
```

## 已知限制

- 盲测每组 3 次、其余功能验收每组 1 次，样本小；场景和产品出自同一人，不是独立的人工金标准。
- 只在 macOS APFS（不区分大小写）上测试过，Windows 完全没测。
- PDF 默认只读前两页，没有 OCR；BM25 不翻译查询，中文查询找不到英文论文。
- 不支持复制、覆盖同名文件、合并文件夹、清空回收区；单个计划最多 500 项。
- 旧写入工具（去重、分类执行）还没有接入新执行器的资料库锁；文件系统和 SQLite 不是统一事务。
- 待办和优先级见 [HANDOFF.md](HANDOFF.md) 第 8 节。
