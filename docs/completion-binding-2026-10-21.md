# 完成条件本地绑定与动作归属

日期：2026-10-21。对应[真实模型复验](live-acceptance-2026-10-21.md)中的三次误报 partial、去重与空目录组合任务的误拦截，以及已恢复错误仍显示为当前阻塞。本次只做离线实现与测试，未调用付费模型，**不代表真实模型验收已通过**。

## 问题归因

三次误报 partial 都不是文件结果错误，而是机器契约由模型自由填写，本地只在收尾时才发现无法核验：

| 复现 | 直接原因 | 架构问题 |
| --- | --- | --- |
| root_only | tool_success(list_dir) 对应的调用发生在 set_task 之前，没有记录为观察 | 观察只在任务存在后记录，任务修订时又全部清空；证据受调用顺序影响 |
| real_classification 第二轮 | file_plan_verified 的 reference 留空，回执存于具体 X 标识下 | 计划与目标之间没有本地绑定，空引用在核验时查空 ID |
| cross_turn_correction 第一轮 | 普通移动使用分类专用 plan_applied | 预检只检查枚举和快照，不检查条件能否由当前执行器满足 |

dedup_cleanup 则是另一类问题：empty_directories_removed 被当作整个目标/步骤的禁止规则，同一目标中的去重回收也被拦截。

## 设计

### 1. 引用由本地确定性绑定

- prepare_file_plan 成功后，在任务上记录 `file_plan_bindings[X] = 目标列表`。file_plan_verified 的 reference 留空时，核验本目标绑定的全部已执行计划；没有执行过的计划会明确提示“已准备尚未执行”。
- 半途中断的计划在绑定中记录未完成动作；之后其他计划必须覆盖这些动作，否则目标不通过，不会因为另一份小计划完成就误判全部完成。
- 分类桥接计划把对应 P 标识绑定到含 plan_ready/plan_applied 的目标。
- 去重回执、分类计划和证据只绑定到当前步骤中确实核验该类对象的目标，减少多目标步骤的引用歧义。
- set_task / edit_task 中模型显式填写的引用，必须在登记前能唯一绑定：file_plan_verified 只能引用本任务已准备的计划，P/R/E 必须在当前会话中存在。否则立即拒绝，并提示留空由本地绑定。
- 本轮运行中、任务登记前的只读调用会归入随后登记的任务；同一运行内修订任务时保留成功观察，已改动目标的标签被移除。tool_success 如写明参数，参数本身就是绑定条件，可匹配未打标签的调用，但不能匹配其他目标步骤的调用。tool_success 仍然只能证明调用成功，仍需复核。

### 2. 条件与执行器的兼容性前置检查

能力注册增加 `produces`，声明执行器会写出哪类回执：去重工具写 receipts，apply_classification 写分类执行记录，通用计划写文件计划回执（分类桥接时两者都写）。这是协议元数据，不是关键词路由。

plan_applied、receipt_verified 两类执行回执条件尚未绑定对象时，如果某个动作属于该条件核验的工作（分别是移动、回收普通文件），而当前执行器不会写出这种回执，就在预检阶段拒绝。拒绝信息会说明应使用的执行器，或建议通过 edit_task 改为相符的条件；修改条件仍需用户确认，不会自动删除或弱化。

### 3. 每个动作带本地确定的目标归属

`claims` 根据完成条件判断动作服务的目标：files_placed 的执行前清单、empty_directories_removed 范围内的空目录、path_absent/path_exists 的路径、执行器回执类型等。没有任何条件认领的动作，保守地归属全部候选目标并承担它们的全部约束。

- 计划步骤保存各自的 goal_ids；目录创建继承其中动作的目标；操作日志按动作记录目标，max_count 计数也按动作归属。
- 约束校验逐个动作进行：目标级约束只作用于归属该目标的动作；全局约束（goal_ids 为空）和 allowed_effects 始终作用于全部动作。
- 空目录保护也逐个动作检查：清理范围内的非空目录或文件，只有被同组其他条件（如去重回执）认领时才放行，否则仍按原规则拒绝。
- 已有复合任务的 prepare_file_plan 可以省略 goal_ids。全部动作都能由条件认领时，本地完成归属；有动作无法认领时才要求模型补充。计划路径不再借用全局 active_step。

### 4. blocker 生命周期

blocker 记录来源（工具）、对象（计划/编辑/任务/目标或参数）、任务版本、状态和解决原因：

- open：未解决，在非完成状态的主答复中展示。失败的写操作即使任务其余部分已完成也继续展示。
- resolved：同一来源、同一对象的后续调用成功；或者计划执行成功，或同目标的后续计划执行成功。
- superseded：任务已修订，或同一对象后续失败给出了新的原因。
- 已解决和已取代的 blocker 不出现在主答复中，而是进入“已恢复的阻塞”详情；不会无条件清空。旧写入失败也纳入同一记录，不再单独按“最近一次参数”推断。

## 模型可见协议变化

- 未新增或删除工具，也没有新增必填字段。
- `prepare_file_plan.goal_ids` 从“多目标必须提供”改为“可省略，无法确定时才要求”。
- `CompletionCondition.reference` 的说明改为“通常留空，由本地绑定”；任务指引中补充 plan_applied、receipt_verified 的适用范围，并说明 prepare_file_plan 不需要先 begin_step。
- 预期请求数影响：省略 begin_step/goal_ids、引用留空可以减少一次协议往返。条件不兼容时会多一次 edit_task + apply_task_edit，但比原先执行完成后才报 partial 再修复要少。该预期未经过真实模型验证。

## 限制

- 只对执行回执类条件做兼容性拒绝。files_placed、path_* 与计划路径的矛盾没有前置拒绝，因为交换、暂存等多阶段计划的中间状态本来就可能与最终条件不同，仍由收尾核验判断。
- 未被认领的动作按全部候选目标处理，这是保守做法，可能要求模型补充 goal_ids。
- root_only 现在是 needs_review 而不是 completed：tool_success 不能证明模型报告的数量正确，主答复也不显示模型给出的数量说明。是否要用本地统计结果绑定“报告数量”类目标，需要另行设计。
- 计划执行成功时，会把同目标较早计划的执行失败标为已解决。真实失败仍会通过目标核验暴露，例如部分执行覆盖检查和 files_placed。

## 后续：真实复验后的补充修复

本设计之后经过三轮真实复验，又发现并修复了几处同类问题，详见[下午复验记录](live-acceptance-2026-10-21-rounds.md)：

- **未归属引用**：证据、去重回执等引用在任何步骤之外产生时，如果任务中只有一个目标核验这类对象，就绑定给它；有多个时仍不猜测。
- **回执对象的位置**：去重回执沿本任务回执之后记录的移动追踪保留件当前位置，再比对哈希；由本任务日志回收的文件，其证据仍有效。
- **max_count 计数**：执行器逐步重查时按 action_id 去重，避免已执行动作被计两次导致计划半途停止。
- **契约与计划矛盾的提示**：准备计划时，若 files_placed 清单仍有未覆盖项，或 path_exists/path_absent 与计划动作冲突，就在返回中附上提示，建议用 edit_task 修正。这只是提示，核验口径不变。上文“限制”中提到的 files_placed、path_* 没有前置检查，现在有了这一层提示，但仍不拒绝。
- **未执行的写任务**：写任务从未执行任何操作时，状态为 waiting_input。
