## 1. 总体判断

保留单 Agent、由本地协议约束权限与证明的方向正确。草案没有通过引入额外意图分类调用解决所有问题，也没有建议放宽权限或提高提示上限；能区分已有用户决定、历史日志、离线复现和推断，这一点符合项目现状。

本次退回不是否定方向，而是以下具体契约仍有矛盾或空缺：幂等查询顺序、普通消息重试、整体取消语义、首批依赖顺序、静态协议容量，以及确认结果来源的实施批次。它们会影响重复操作、错误完成、用户取消是否生效及改造是否能落地，不能只列为实施时再考虑。

本报告的 P0 指可造成未经授权写入、重复写入或错误证明业务完成的阻断风险；P1 指实施前必须明确的核心契约；P2 指可以分期完善但应有负责批次的事项。已复现的现状 P0 不等于方案又新引入了一个已经复现的 P0。

## 3. 必须修订的问题

### R1 · P1：已接收请求的幂等查询必须早于可变问题状态校验

对应草案：4.4、13。

场景：Q1 的 A 已被接收并执行，网络丢失响应；系统随后产生 Q2，或者 Q1 所属任务进入新 revision。浏览器携带原 client_message_id 重试 Q1。

问题：4.4 写成“校验会话和版本 → 检查 client_message_id 唯一性”。若先校验 Q1 是否仍 open、是否仍属当前 revision，正常重试将被当成已回答或过期请求拒绝，违背同节“返回原 receipt”及第 13 节的验收要求。用户会看到发送失败，可能再发新消息，增加重复执行风险。

必须修正：先完成会话/root 的访问检查；再以该隔离域的 message_id 查询已接收记录并比较规范化 payload。相同 payload 返回原 receipt/turn/run，即使问题此后过期、已答或任务已修订；不同 payload 返回幂等冲突。只有首次接收才校验当前问题/任务版本、CAS 消费并写 outbox。不可为了返回原结果绕过当前会话访问检查。

验收：同 ID 在 Q2 出现后、任务 revision 改变后、进程重启后，均返回 Q1 原 receipt，且不新增 turn、模型调用或文件操作；同 ID 改 payload 始终冲突。

### R2 · P1：幂等不能只覆盖选项回答，普通请求也必须有明确事实源

对应草案：4.4、4.5、11、12 的 A1-输入。

场景：用户输入“把 a 移到 Archive”，服务端已接收或部分执行，但 POST 响应丢失；浏览器重试同一条自由文本消息。另一种情况是先提问后用户用自由文本修改目标，重试该消息。

问题：新 API 允许 response 为空，但数据库唯一键和 outbox 主要围绕 answers.question_id、answers.client_message_id、run_requests.answer_id 描述。普通请求没有 answer_id 时，如何在模型调用前持久化唯一接收事实、如何原子登记 outbox、如何返回同一个 turn，尚未明确。requests.source_message_id 唯一不自动保证消费和 UI 建 turn 幂等。不能对外笼统承诺“请求幂等”，实际只保证按钮回答。

必须修正：明确所有消息共同的接收记录与唯一键（可直接扩展 run_requests，不强制增加一张表）；answer_id 是可选关联。普通消息、新请求、自由文本修订、结构化答案统一走接收/CAS/入队规则。前端为一次提交在发送前生成并保留 ID，失败、刷新或重试复用，用户修改文本则生成新 ID。CLI 明确复用 message_id 的规则。不要按文本相同去重，因为用户可能有意再次发送相同请求。

验收：上述四类输入分别测试“响应丢失、入队后崩溃、重启后重试、同 ID 不同正文”，同一次提交最多一个 durable run request 和一个 UI turn，不重新启动已运行但结果不明的写入。

### R3 · P1：整体取消、局部跳过、暂停必须分别定义，尤其是部分执行后取消

对应草案：4.3 的 cancel_request、4.5、5、7、13。

场景：a 已移动，b 因同名冲突等待选择。用户选择“取消整个请求”，或输入“算了，剩下都别做了”；另一种情况是尚未登记任务就选择全部取消。

问题：草案提供 cancel_request，但第 5 节将“取消/跳过”统称 skipped_by_user，第 7 节没有整体取消事件的 reducer 规则；4.5 也没有说明自由文本取消怎样落到已有 TaskPatch.cancel。若把所有剩余目标跳过，可能聚合成 fulfilled 并显示“已完成”；若只挂一个取消标记，又可能留下可继续消费的旧问题或 queued run。

必须修正：定义用户意图“跳过这部分”“本次不继续/暂停”“取消整个请求”的转换；不要求再增加一次固定确认。整体取消必须使请求不可继续写入、关闭相关问题和未运行队列，保留已完成动作、历史授权与审计事实但不再可用于未来执行。任务已存在时明确与现有取消修订机制的关系；登记前取消无需为记录取消而创建写任务。取消不自动撤销，恢复需要显式恢复与重新预检，旧答案不得重激活。运行中无法安全即时停止时必须报告到哪个边界停止，不能承诺已打断正在执行的文件操作。

验收：零执行取消显示“已取消”；部分执行后取消显示“已取消；此前已移动 a，b 未处理，可撤销”，flow=cancelled，业务结果保留 partial，不能改写 a 为未执行或宣称整体完成；取消后旧按钮、重复消息、已排队的续做均不得启动新写操作。新增请求不继承旧选项/敏感读取授权。

### R4 · P1：首批实施顺序与真实依赖相反，需要先封住错误完成路径

对应草案：1、5、6、12、13。

场景：按当前 A1→A2 发布顺序，先上线新问题/局部选择。第 5 节又明确要求先精确归属，再按目标应用决定，而精确归属在 A2；已有“只移动 a 却将 b 判完成”的 P0 也要等 A2。

问题：A1 的业务正确性依赖 A2，却被写成可以先独立发布；同时 Request、draft 映射、outbox、CLI/Web、输入关系、终止协议都压进 A1。这样首个发布物并不小，也未明确哪些代码可以独立启用。

必须修正：列出依赖图与可发布切片。建议 A0 冻结复现后，优先交付最小 strict_goal_binding（含新旧模糊计划的安全恢复规则），再做精确问题/消息幂等，之后启用局部决定与草案映射；同类去重/只读 claim 可接续。强终止 schema 原子切换应有独立闸门，不成为问题 ID 和精确回答的强制前置。若采用其他顺序，必须证明每一片在缺少后片时仍安全，并明确只集成不启用的部分。

验收：每个可发布片都有独立开关组合、数据迁移、回滚去向、测试门槛；不得发布 A1 却依然按多认领证明判完成。调整后重估工作量，不能简单把原 4–6 人日当成全部交互重构的承诺。

### R5 · P1：静态协议容量是实施可行性条件，需要具体原型和停止线

对应草案：4.1、4.5、6.2、6.3、10、14。

场景：需要加入 finish_turn、input_resolution、scope/draft 映射、专用工具 part、evidence_bindings 等字段，又不能增大 31,311 字符上限。

问题：现有文档基线只有约 264/355 字符余量。草案虽要求差额表和删减重复说明，但没有展示能容纳上述字段的 schema 原型，也没有把“无法容纳”的结果转成明确范围决策。首批直接批准全部接口改造，工程师可能做到中途才被迫压缩关键安全说明或扩大 cap。

必须修正：把无付费调用的 schema/提示原型、当前基线复测和逐项增删表列为 A0 硬交付；给出拟删除/合并的具体说明来源和语义保留检查。强终止切换必须等两种敏感配置均符合 cap、旧控制 schema 不重复暴露、纯问答脚本回归通过后启用。若不能容纳，先交付本地身份/存储/精确回答/现有 Action.part 的正确性改造，延后额外协议字段，不能提高上限或删掉用户既定安全约束。

验收：文档附可复现的字符差额与最终 schema 候选；两配置均≤31,311；纯聊天、只读、提问、写入的正常路径不增加固定 LLM 调用；真实模型的修复率/费用/缓存只是后续授权验收项，不能由离线脚本宣称已证明。

### R6 · P1：首批要求区分拒绝/超时/断连，却把必要传输改动放到 B2

对应草案：8、12 的 B2、13。

场景：用户在确认卡 15 分钟未回答，或断开页面；当前 webapp 会把超时变成 n，Confirmer EOF 也返回 n，执行器最终写“用户拒绝”。模型随后可能重新提交同一计划。

问题：草案的验收明确要求区分三者，但错误来源和确认结果结构都排在 B2，A1/A2 的发布门槛和代码清单没有相应最小改造。单靠错误枚举不能恢复入口已经丢失的事实；重复检测也不能保证第一次拒绝后就不再弹卡。

必须修正：把最小确认结果来源保留和拒绝后续规则纳入首批，或明确首批不宣称解决且将相应门槛限定为后续批次。建议首批仅补 terminal outcome=approved/declined/timed_out/interrupted 的本地结果与报告，无需提前迁移所有 ToolResult。至少同一计划/同一规范化 manifest 被明确拒绝后，本轮不得自动重弹；完整等价拒绝指纹仍可后续实施。超时/断连不能当同意，也不能假称用户主动拒绝；人工重新尝试需要重新预检和新的确认。

验收：Web 显式拒绝、Web 超时、CLI EOF/中断、确认提交响应丢失分别有固定结果；零未授权写入；不自动重弹同一拒绝清单；部分已执行事实始终可见，不因后续拒绝被抹掉。

## 4. 建议补充的 P2 项

### R7 · P2：迁移/兼容需要开关矩阵和单一写入权威

对应草案：11、12、14。

现有 backup API、事务迁移、outbox、旧问题 unknown scope、禁止用旧 DB 覆盖已执行文件的方向正确。需要补一张具体组合矩阵：旧 API/新 API、旧会话/新会话、旧按钮/新按钮、strict_terminal 开/关、structured_answers 开/关、strict_goal_binding 开/关。标明每种允许组合读取与写入哪份事实，禁止组合启动时直接拒绝或降级只读，不能靠实施人员猜。

尤其不要把 legacy pending_choice 与 questions 当两个可独立消费的主状态；旧格式应是同一事实的投影，消费不双写竞争。需要明确 schema_version 是数据库版本、会话协议版本还是服务配置，避免回滚适配器后又创建旧格式的新活跃问题。验收包含进程在迁移/投影交接处中断、旧会话刷新和回滚后恢复，并保留已执行日志及已答事实。

### R8 · P2：找全的覆盖成本与语言扩展成功率需分别验收

对应草案：9、13。

草案已正确区分枚举完成、抽取完成与语义找全，且翻译关键词使用常规模型请求。建议补充固定样本：中文问英文资料、中文问中文资料、0 命中但抽取完成、0 命中且 OCR 未完、文件中只有后几页相关、候选超过 top_k、库内容在扫描间改变。记录已审/总数/未审原因、查询数、实际读取数、OCR 单元数和费用；coverage ledger 必须绑定 scope/index/file version，不能把前一版全库的已审数用于新文件版本。

检索覆盖 ledger 无需为了显示完整度为每次普通检索扫描全库。找全做不到时直接报告缺口，不再追加一个“还要不要继续”的固定确认；用户主动续做仍沿用现有累计读/检索预算。C1 暂不承诺召回提升比例，先保存可衡量基线。

## 5. 已认可、应保留的设计

- 问题先持久化再展示；按钮以 question_id/option_id/version 精确提交；裸字母没有身份时不承诺自动去重。
- 登记前可以提问，Request 没有写权限；局部问题必须显式映射到正式目标，不靠目录相近猜归属。
- 问题答案与具体文件操作确认独立；敏感检测默认关闭，开启后仅点选可以授权读取，文字回答不能授予读取权。
- 多目标业务动作精确归属；同类 dedup 显式 part；回执与证据由本地生成，模型不能声明自己已完成。
- 流程结束、业务结果、机械检查、语义复核分开；只读界面继续“已回答”，不得靠修改评测把旧失败刷绿。
- 单计划 500 项、不自动拆批、不覆盖、隐藏文件规则、可撤销、限制不可暗改、费用按轮和读取按任务累计的现有语义保留。
- 不默认动态换工具、不额外增加意图分类调用、不恢复旧快照堆积；付费模型和真实浏览器是单独证据层级。
- 分库 outbox 只解决交接，不声称文件系统和数据库统一事务；inflight 不明不能自动重放。
