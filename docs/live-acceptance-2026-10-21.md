# 本地执行优化后的真实模型验收

日期：2026-10-21。实际调用项目配置的 DeepSeek `deepseek-flash`，复跑同一套 8 组/10 轮生产 Agent 回归。不是脚本模型、不是仅测 API 连通性，也不是网页部署或浏览器现场验收。

**结论：文件结果改善，但整体未通过。** 8/8 组的本地文件结果、内容保护和撤销断言通过；3 轮正确执行却误报 partial，部分已恢复的历史错误仍显示成当前阻塞。总体模型往返和费用没有下降。不能用评测脚本的退出码或 `passed_local=8` 宣称整体验收通过。

## 方法

- 使用完整生产提示词、工具 Schema、任务运行时和当前配置。每轮使用现有 max_steps=25、task_repair_limit=6、单轮费用软预算 ¥0.30；评测总软预算 ¥1.20，关闭 API 自动重试以记录明确的实际请求次数。
- 每组在临时沙盒中生成数据；6 篇真实论文复制并改为中性文件名。金标准只供评测检查，不进入模型输入。确认自动允许只作用于临时文件，不能代表用户手动确认体验。
- 同一组的后续轮保留历史、文件身份和任务状态。按实际文件内容/位置、任务状态、最终答复分别检查，结束后按逆序撤销并验证原始布局。
- 全过程冻结 agent/tools/safety 产品代码，不根据中途失败热修；真实论文原件哈希前后相同。临时数据结束后清理，原始脱敏历史、事件、确认和结果保留。历史不保存 reasoning_content。
- 基线为 2026-10-20 同套 10 轮实际 Agent，不把当天其他探针请求混入比较。本套是已知回归集，非新盲测；跨天服务延迟、采样和缓存状态不可控，不据单次结果推导稳定性能或总体理解率。

## 三次误报 partial

1. 根目录统计与移动：文件全部正确，最终回答也报告了数量 2，但模型增加 `report_count` 目标，`list_dir` 观察没有绑定到它，导致 tool_success 条件失败。调查证据仍受调用顺序/步骤绑定影响。
2. 六篇分类计划执行：本地已完成全部移动，files_placed 通过；模型自行登记 `file_plan_verified` 却留空 reference，本地回执保存在具体 X ID 下，核验查询空 ID 失败。该条件本应由本地生成和绑定，当前仍暴露给模型填写。
3. 跨轮更正的第一轮：普通文件移动正确，但模型选择了仅适合分类计划的 plan_applied 条件，无法找到分类引用。第二轮更新同一个任务并正确移回 b.txt 后完成。单次条件类型合法不代表适用于此操作。

原来无效选择快照被接受的问题本轮确实前置拦截：跨轮第一轮的错误 mapping 在登记阶段拒绝，没有按无效清单写入。但其他不适用或缺引用的验收条件仍会漏过前置检查。

## 调用仍然偏多的原因

- 新执行器已经被采用，多轮出现 prepare_file_plan / execute_file_plan，但模型仍先调用 set_task、填写底层权限/约束，再进入新路径，形成两套协议叠加。
- 根目录移动由 4 次增到 10 次；包括非法副作用 delete、遗漏源写范围、编辑/确认修复。应用领域任务也仍先生成不适用的 create+same_extension 规则，随后修复范围；并非一次语义判断后全由本地完成。
- 去重与清空目录由 6 次增到 18 次：模型将两个目标一起绑定，空目录完成条件误作用于去重文件。它先尝试 deduplicate、apply_dedup，再尝试通用计划、直接 trash，最后经过任务编辑拆开处理。六次工具失败分散在不同错误类/进展之间，没有触发本轮的无进展停止预算。
- 新增工具和参数继续扩大选择空间。减少了局部工具数，但模型请求总数仍增加。单纯再叠提示词或新增工具没有关闭旧的复杂编排入口。
- application_dimension 最终本地检查通过、只等待语义复核，但正文仍展示已修复的旧源写范围错误。TaskRuntime 用 tool 标识记录 blocker，而成功执行只清同一 plan_id 的 blocker，生命周期未统一。
- PDF 缓存确有命中：无答案检索中 3 次抽取 miss、后续 3 次 hit；但总体模型耗时仍约 99%，缓存不替代减少编排往返。

只讨论任务的回答仍较长；无匹配检索仍输出三份逐篇否定表格。这不是本轮最主要执行故障，但简洁输出目标尚未达到。

## 后续修复优先级

1. 将文件操作的机器完成条件及引用绑定收回本地；对模型的用户意图/对象提案提供单一入口。不要让模型先填底层任务表再调用计划生成器。已有约束仍需保留并经明确确认才能变更。
2. 由计划的具体操作声明目标归属。组合任务的去重和空目录清理按动作绑定约束，不能依赖一个可变 active_step 同时代表多种用途。
3. 验收预检检查条件与操作是否兼容、引用是否能确定绑定，不只检查枚举值或已有快照。保留明确的当前状态与执行事实边界。
4. 统一 blocker 的来源、对象、版本和解决状态；最终正文只展示尚未解决的原因，已恢复错误进入过程详情。
5. 修复后增加未参与调试的新组合场景，并重跑同一套回归；同时断言文件、状态和主答复，不再以 `passed_local` 作为总验收结论。

本轮只做真实测试与记录，未根据失败修改产品代码。
