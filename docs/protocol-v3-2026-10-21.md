# 协议 v3（P1-4）：模型只提交意图和对象，契约由本地编译

2026-10-21 晚实现。目前只做了离线验证，**还没有用真实模型复验**。下文的请求数是脚本回放得到的下限，不代表真实模型的表现。

## 为什么要改

基准数据取自第 04、05 轮真实复验，回归套件和 holdout 各一套，共 244 次模型请求、307 次工具调用。见 [live-acceptance-2026-10-21-rounds.md](live-acceptance-2026-10-21-rounds.md)。

- 有 67 次请求（**27%**）只做了协议纠错，没有做别的。纠错调用包括：失败的 set_task、prepare 或 execute；第一轮里模型为了修改自己写的契约发起的 edit_task 和 apply_task_edit；begin_step。这类调用共 79 次。
- set_task 调用 34 次，失败 15 次；prepare_file_plan 调用 39 次，失败 17 次。
- set_task 和 edit_task 两个 schema 合计 13.3k 字符，占全部工具 schema 的 40%。

按 trace 里的 ERROR 文本归类，以及 v3 对各类问题的处理：

| 失败类别 | 次数 | v3 的处理 | 只在 v3 生效？ |
| --- | ---: | --- | --- |
| write_roots 只写了目标，漏了要移动的来源 | 7 | 本地从清单推出写入范围，超出的部分列在确认卡片里 | 否 |
| 模型自己写的规则有误：max_count 把目录算进去，within、name_glob、selector 写错，缺 limit | ≈10 | 模型不再写规则，只填 `limits`，由本地编译；`max_files` 不统计自动创建的目录 | 是 |
| files_placed 的映射和执行前清单对不上 | 4 | 模型看不到 files_placed，organize 部分统一用 file_plan_verified | 是 |
| move 的 destination 写成了目录，或者重复声明本来会自动创建的目录 | 6 | 按 `mv` 语义理解：目录存在、由本计划创建、或多个文件指向同一路径时，都视为"放进这个目录"；重复的 create 合并成一项 | 否 |
| 修订任务后，旧计划提示版本已变化 | 3 | 还没开始执行的计划按新版本重新生成（变基），重新预检和确认 | 否 |
| 旧写入工具缺 begin_step | 3 | 有且仅有一个部分核验这类回执时，自动归给这个部分 | 否 |
| JSON 写坏了，或者参数被多套了一层 | 4 | schema 变小了，但不保证能消除 | — |
| 文本约束没有映射成规则，写入被拦 | 2 | 列在确认卡片里，用户确认后可以写入，任务保持 needs_review | 否 |

"只在 v3 生效"一列为"否"的，是本地执行层的改动，v2 协议同样受益。所以做 v2 和 v3 的真实对比时，差异只来自模型能看到的协议（工具集、提示、schema），不包括这些容错改进。

## 提示词是否不够精确：归因分析

结论：**有一部分是提示词的问题，但"反复调用"并不是模型在原地打转，也没有发现事实性幻觉。**

数据来自 `eval/protocol_errors.py`，统计第 04、05 轮全部 trace。这个脚本只读结果目录，不会修改它们。

| 指标 | 数值 |
| --- | ---: |
| 请求 / 工具调用 / 被拒绝调用 | 244 / 307 / 43 |
| 纯协议纠错请求 | 67（27.5%） |
| 完全相同的重复调用 | 19 次，全部发生在状态变化之后（修订、begin_step、写入），没有一次原地打转；重复检测从未触发 |
| 写入后又用 list_dir 或 file_info 复查 | 9 次（提示里已说明不必复查） |
| 用户没提数量，模型自行设置数量上限 | 8 次 |
| 被拒绝的类别 | 规则 9、目标路径 9、完成条件 6、写入范围 5、计划过期 3、缺少步骤 3、schema 结构 3、文本约束 2、JSON 写坏 2、应走编辑流程 1 |

judge 的"主答复"维度在这 4 套里全部通过；no_answer 场景没有编造结果；提示注入照做 0 次。下面按原因分四类：

1. **v2 提示互相矛盾**，这是直接原因：
   - `SYSTEM_V1` 里的"先 make_dir"和"父目录由本地生成"冲突，导致显式声明 create，进而目标重复；
   - "首次使用 set_task 表达完成条件"和"新任务不必先 set_task"冲突：模型 34 次都先写 set_task，捷径从来没被用过；
   - "约束需映射到 rules，包括数量上限"这句话，诱导模型在用户没提数量时 8 次自行加 max_count。
2. **schema 缺少语义说明**：
   - `OperationRule.predicate` 和 `selector` 没有 description，模型把 within 当成了"保护"；
   - v2 的 `Action.destination` 没有说明必须写完整路径，模型写成了目录；
   - `CompletionCondition` 是扁平结构，模型 6 次给不需要 tool 字段的条件填了 tool。
3. **报错信息不精确，模型就去猜原因**：这才是"幻觉"的主要表现。max_count 的报错不给计数，模型就编出"目录创建也被计入"的解释，并把自己设的上限从 3 放宽到 10。现在已经改了：数量超限时列出已计入的项、本次新增的项和计入范围，并提示"不要自行放宽"；规则冲突时写出规则含义；部分执行过的计划过期时，写出版本号、进度和下一步。
4. **不属于提示问题**：本地 bug（重复计数、来源已回收时崩溃，均已修复），以及长参数下的 JSON 格式错误。

v3 从结构上消除了第 1 类，以及第 2 类的大部分；第 3 类的改动在 v2 和 v3 下都生效。**v2 提示保持冻结**，不修第 1 类问题，作为对照基线；这些矛盾记为 v2 的已知缺陷。下一轮真实对比要用同一脚本输出两种协议各自的分类，来回答"提示词改进消除了多少错误"。

## 授权边界

用户在 2026-10-21 确认了两点：

1. 写入范围由本地推导，超出部分列入确认卡片；
2. 文本限制列入确认卡片，用户确认后可以写入，结果保持 needs_review。

| 由谁决定 | 内容 |
| --- | --- |
| 模型 | 用户意图的摘要；任务分成哪几部分，每部分是什么类型；具体对象，即动作、选择集或分类计划 ID；用户**明确说出**的限制；需要用户回答的问题 |
| 本地 | 各部分的完成条件；写入范围（来自计划清单里的精确对象）；允许的副作用（由部分类型决定，再减去用户禁止的）；动作归属到哪个部分；父目录；计划变基 |
| 用户 | 确认精确清单就是授权。超出原登记范围的对象会在卡片上单独列出；修改任务时，卡片上列出差异 |

不变的规则：

- 用户限制编译成 `constraints`，只能收紧，计划不能绕过。违反限制的计划在预检阶段就被拒绝，不会进入确认。
- 只读任务（没有任何允许的副作用）不会因为某个计划而获得写权限。推导只补路径，不补副作用。
- 被拒绝的确认既不写入，也不授予范围。`scope_grants` 记录每次授权对应的计划和运行。
- 同一轮运行里不能用第二次 `start_task` 另建任务，避开已经登记的限制。

## 模型看到的协议

```
start_task(summary, parts=[{id?, kind, description, scope?, execute?}], limits={...}, questions=[], criteria=[], detail)
  kind ∈ find | dedup | organize | classify | answer
  limits: no_effects, keep_unchanged, only_within, only_extensions, max_files, notes
prepare_file_plan(description, actions | selection | classification_plan_id, task_id?)   # 唯一的文件写入口
execute_file_plan(plan_id)
revise_task(task_id, expected_revision, reason, parts?, remove_part_ids?, limits?, questions?, cancel?)  # 预览和确认合成一次调用
finish_task(summary)
```

在 v3 下，模型看不到 set_task、edit_task、apply_task_edit、begin_step、move、rename、trash、make_dir 和 apply_classification。这些接口在代码里都保留，供 v2 对照和旧测试使用。

### 每类部分的完成条件模板

见 `agent/intent.py` 的 `TEMPLATES`。所有引用都留空，由本地绑定。

| kind | 完成条件 | 人工复核 | 需要的副作用 |
| --- | --- | --- | --- |
| find | evidence_valid | 是 | 无 |
| dedup | receipt_verified | 否 | trash |
| organize | file_plan_verified | 否 | create、move、rename、trash |
| classify | plan_ready；`execute=true` 时为 plan_applied | 是 | `execute=true` 时为 create、move |
| answer | manual_review | 是 | 无 |

### 修订和续做

- `revise_task` 用同一个 ID 替换某个部分。被改写的部分不再沿用旧计划的绑定（`TaskStore.inherit_execution`），因为一个计划只能证明它当初准备时对应的那个目标。用户更正后，模型要按新要求准备新计划。
- 续做近期任务时，在 `prepare_file_plan` 里填写 `task_id`，沿用原任务的限制，不能借此切换到别的任务。

## 2026-10-21 深夜：用户运行暴露的问题与选择题策略

来源：用户在网页里的一次真实运行，日志为 `logs/20261021-224026-606418.trace.jsonl`，请求是"把文献文件夹里的所有内容平铺到根目录并删除空文件夹"。这次运行用了 20 次请求，其中 6 次 prepare_file_plan 失败；`文献` 文件夹本身没有被删除，主答复却写着"本地核验通过"。

### 原因

1. 同一个计划里先移出文件、再回收这些文件夹：计划在准备时就核对每个对象，那时文件夹还不是空的，于是报了一条泛泛的"非空目录"。
2. `文献` 里只剩一个隐藏文件 `.DS_Store`：列表工具不显示隐藏文件，所以模型看到的是空文件夹。它换了 3 种路径写法重试，最后编了一个错误原因。
3. 核验只检查已执行的计划，用户要求删除的 `文献` 本身没有被核验到，所以显示为通过。

### 修复（提交 `eaba390`）

- **非空目录的报错列出事实**：报错里列出目录中的条目，隐藏文件单独列出。如果目录只含隐藏文件，报错说明"本工具不处理隐藏文件，请用户在 Finder 中手动删除，或保留该文件夹，不要再换路径重试"。用户选择了 B：这类目录仍然不回收。
- **同一计划内先移出再回收**：报错说明要拆成两个计划，先执行移动，再单独回收。
- **`finish_task.unfinished`**（仅 v3）：模型声明哪些部分没有做到，这些部分标为未完成，任务状态变为 partial。这个声明只能把状态降级，不能升级；复核重新计算后依然保留。

### 选择题策略（`ask_user`，仅 v3）

- **参数**：问题、反问原因类别、2–4 个具体选项、是否允许用户自行补充。反问原因类别有五种：多个候选对象、标准没有界限、冲突未交代、超出范围、无法按原样做到。
- **调用后**：本轮结束，状态为 waiting_input，本轮不再写入；主答复用字母列出选项，网页上渲染成按钮。
- **下一轮**：用户只回复一个字母时，本地把它解析成"选择 B. ……"并写进协议说明；用户回复自由文本时，标注为对上一问的补充回答。
- **提示规则**：只在以上五类情况下提问；惯例默认和能用只读工具查清的事实不问；提问前先查清事实，让选项具体。
- **测试**：新增 5 项，离线测试共 565 passed。网页按钮通过了 JS 语法检查，**尚未在浏览器中实际查看**。
- **尚未做的**：E4 实验，即"该问的时候问了"和"不该问的时候多问了"的真实测量。歧义场景集和清晰场景集都需要用新的盲测场景来测。
